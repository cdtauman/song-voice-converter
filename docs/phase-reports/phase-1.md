# דוח סיום — Phase 1: Compatibility Spike + שלד

**תאריך:** 17 באוגוסט 2026
**מכונת הפיתוח:** Lenovo 83DJ · Intel Core Ultra 7 155H · 15GB RAM · Intel Arc Graphics
**סטטוס:** ✅ **הושלם** — כל סעיפי ה-DoD עברו.

---

## 1. מה נבנה

### שכבת החומרה — שלושה מסלולי ביצוע

SongVoice יכולה להריץ עבודה כבדה על אחד משלושה מסלולים, **כולם יעדי ליבה**:

| מסלול | חומרה | סדר עדיפות |
|--------|--------|-------------|
| **CUDA** | כרטיסי NVIDIA | 1 |
| **XPU** | Intel Arc / Core Ultra עם Arc משולב | 2 |
| **CPU** | כל מחשב | 3 |

הרכיבים: `ComputeBackend` (שלושת המסלולים), `DeviceManager` (זיהוי ובחירה),
`SupportMatrix` (מה אומת לכל רכיב).

### ⭐ כלל ההוכחה — שתי רמות

> **OPS** = הוכחת תאימות בלבד: סט האופרטורים החשוב של הרכיב רץ והחזיר תוצאה תקינה.
>
> **END_TO_END** = הרשאה למסלול ייצור: **המימוש האמיתי שנבחר למוצר** רץ מקצה לקצה
> על אותו backend.

התקנה נקייה, ייבוא מוצלח או `is_available() == True` — לא מוכיחים כלום.
וגם OPS **לא** מספיק כדי לשלוח מודל אמיתי למאיץ בזמן שימוש רגיל.

**רק `END_TO_END` של המימוש הרלוונטי מאשר routing של ייצור.** כל דבר אחר נשאר
על CPU עד שהמודל האמיתי נבדק. כך לא נקבל בעתיד מצב שבו RoFormer או RVC נשלחים
ל-XPU רק משום שסט אופרטורים דומה עבר smoke test.

**כל רכיב נבחן בנפרד.** אין הנחה שמסלול אחד חייב לעבוד לכולם — אחרי שמימוש מסוים
יוכח מקצה לקצה, הוא יוכל להשתמש במאיץ גם אם רכיב אחר עדיין נשאר על המעבד.

### ה-Spike

בונה לכל מועמד סביבה מבודדת, מתקין את הצינור בבת אחת כדי לחשוף קונפליקטים מוקדם,
ומריץ עומסי תאימות אמיתיים. הוכחת תאימות נשמרת, אבל לא משודרגת אוטומטית להוכחת
מודל מלא.

### השלד

מבנה הפרויקט · ארבעת המתאמים שאושרו · `svc doctor` בעברית · הודעת שגיאה בעברית
לכל קוד · תקשורת JSON-RPC בין הממשק למנוע בתהליכים נפרדים · CI עם lint, טיפוסים,
בדיקות, גבולות ארכיטקטורה ובדיקת רישוי.

## 2. מה נבדק, ומה נמצא

### ✅ ממצא 1: מסלול Intel XPU עצמו עובד

`torch 2.13.0+xpu` זיהה והפעיל את הכרטיס:

| | |
|---|---|
| מכשיר | Intel(R) Arc(TM) Graphics |
| זיכרון | 7.8GB |
| יחידות חישוב | 128 |
| דרייבר | 1.15.39183+1 |
| כפל מטריצות | **שגיאה מקסימלית מול המעבד: 0.0** |

לא רק זיהוי — חישוב אמיתי שהמספרים שלו הושוו למעבד ויצאו **זהים בדיוק**.

### ✅ ממצא 2: קיימת תאימות Intel לשלושת תחומי ה-AI — אבל רמת ההוכחה שונה

| רכיב | מה הורץ על ה-GPU | רמת הוכחה | משמעות |
|------|-------------------|------------|---------|
| **הפרדה** | STFT ← Multi-Head Attention ← iSTFT (סט האופרטורים של RoFormer) | **OPS** | תאימות קיימת; RoFormer/PolarFormer אמיתי טרם אושר לייצור |
| **זיהוי גובה** | **`torchfcpe` אמיתי, מקצה לקצה** | implementation-specific **END_TO_END** | FCPE אומת; **RMVPE עדיין לא** |
| **המרת קול** | Conv1d ← Transformer ← ConvTranspose (סט האופרטורים של RVC) | **OPS** | תאימות קיימת; RVC אמיתי טרם אושר לייצור |
| הזזת גובה | — | CPU | מעבד מעצם טבעו (ספריית C++ בלי מסלול GPU) |

הנקודה החשובה: SongVoice משתמשת ב-**RMVPE כמנוע F0 הראשי**. לכן הצלחה מקצה לקצה
של `torchfcpe` נשמרת כראיה ספציפית ל-FCPE, אבל **אינה נחשבת הוכחה ש-RMVPE עובד
על XPU** ואינה מאשרת את מסלול ה-F0 הראשי ל-XPU.

הפרדה תקודם ל-`END_TO_END` כש-RoFormer/PolarFormer האמיתי ירוץ בהצלחה ב-Phase 2.
המרת קול תקודם כש-RVC אמיתי ירוץ בהצלחה בשלב ההמרה. RMVPE יקבל הוכחה נפרדת כשייושם.

### 📌 ממצא 3: מהירות — לא מסקנה, עדיין

בעומסים הזעירים האלה `torchfcpe` היה **פי 2.2 מהיר יותר** על Intel (5.7 שניות
מול 12.4), אבל עומסי ההפרדה וההמרה היו **איטיים יותר** על ה-GPU.

**זה לא מדד לביצועי המודלים האמיתיים** — בעומסים של שניות בודדות, זמן הקומפילציה
והעברת הנתונים יכול לבלוע את הרווח. השוואת המהירות האמיתית תיעשה עם המודלים
והחומר המלא בשלבים המתאימים.

### ❌ ממצא 4: Python 3.12 שבור

ב-3.12 מנהל החבילות בוחר `librosa 1.0.0`, שהסירה את `audioread`. אבל
`audio-separator 0.44.5` עדיין מייבא אותה:

```
ModuleNotFoundError: No module named 'audioread'
```

זו תקלה שהייתה מתגלה רק מאוחר יותר. **הפרויקט ננעל ל-Python 3.11 על סמך מדידה.**

### ✅ ממצא 5: הזזת הגובה MIT עובדת

`python-stretch 0.3.1` הזיזה אוקטבה שלמה והחזירה **בדיוק 44,100 דגימות מתוך 44,100** —
חוזה שימור האורך מתקיים. מאשר את ההחלטה להוציא את Rubber Band (GPL) מהליבה.

### ✅ ממצא 6: ffmpeg מכיל את כל מה שצריך

`loudnorm`, `alimiter`, `acompressor`, `aresample` — כולם קיימים.

### 📌 ממצא 7: torch 2.13, לא 2.11

במחקר נכתב "PyTorch 2.11". בפועל נפתר 2.13.0.
**זו בדיוק הסיבה שלא ננעלו גרסאות מראש.**

### ✅ ממצא 8: אפס תלויות GPL

כל **86 החבילות** שב-`constraints.txt` נבדקו מול PyPI:

| | |
|---|---|
| הפרות GPL / AGPL | **0** |
| LGPL (מותר בקישור דינמי) | 1 — `soxr`, כצפוי |
| ללא הצהרת רישיון | 1 — `llvmlite` |

## 3. `svc doctor` — המשמעות אחרי תיקון רמות ההוכחה

`svc doctor` מפריד עכשיו בין **מאיץ שקיים ועובד ברמת PyTorch** לבין **מסלול ייצור
שאושר למודל אמיתי**. על מכונת Intel הנוכחית המשמעות היא בערך:

```
✅ מערכת ההפעלה                 Windows 11 (build 26200)
✅ גרסת Python                  Python 3.11.15
⚠️ זיכרון המחשב                 15GB — יעבוד, אבל שירים ארוכים ואימון קול עלולים להיות איטיים.
✅ מקום בדיסק                   450GB פנויים
✅ כרטיס גרפי Intel             Intel(R) Arc(TM) Graphics
ℹ️ האצה של NVIDIA (CUDA)        לא קיימת במחשב הזה.
✅ האצה של Intel (XPU)          פעילה — Intel(R) Arc(TM) Graphics (8GB)
ℹ️ האצת חומרה                   XPU זמין; המודלים המלאים טרם אומתו למסלול ייצור
ℹ️ מסלול ייצור לכל שלב          הפרדה: מעבד · זיהוי גובה ראשי: מעבד ·
                                המרת קול: מעבד · הזזת גובה: מעבד
✅ עיבוד שמע (ffmpeg)           זמין, כולל רכיבי המיקס הנדרשים
```

זה **לא מוריד את Intel מיעד ליבה**. זה רק מונע הבטחה מוקדמת. ברגע שמודל אמיתי
עובר `END_TO_END`, אותו רכיב רשאי לעבור אוטומטית ל-XPU.

## 7. תוספת: מדיניות שימוש חוזר + אימות בזמן ריצה

### מדיניות השימוש החוזר

נכנסה לתוקף מ-Phase 2: **לא כותבים מחדש מה שכבר קיים ובוגר.**
לפני כל רכיב מנוע — בודקים את המימוש ב-AI-RVC, Applio ו-RVC-Project,
ובוחרים: שימוש ישיר ← התאמה ← עטיפה ← הכנסת תת-קבוצה ← מימוש עצמי.

הרישיונות אומתו מול GitHub API: **שלושת המקורות הם MIT.**
המדיניות המלאה ב-[reuse-policy.md](../reuse-policy.md), והמרשם ב-[third-party.md](../third-party.md).

מה שנשאר ייחודי ל-SongVoice: מנוע `s = 12k + r`, ניתוח המנעד, `quality_vs_shift`,
בחירת מסלול לכל שלב, הממשק בעברית, ומערכת הבנצ'מרק.

### `svc verify-backends` — אימות על מחשב המשתמש

הפקודה מריצה את אותם עומסי תאימות על החומרה שלפניה ושומרת שתי שכבות ראיה:

- **ראיית רכיב כללית** (`proofs`) — OPS עד שהמימוש האמיתי של הייצור עבר.
- **ראיה לפי מימוש** (`implementation_proofs`) — למשל `torchfcpe/xpu = end_to_end`.

הפלט מסמן במפורש:

```
            cpu     xpu
הפרדה       ✅       🟡
זיהוי גובה  ✅       🟡   ← torchfcpe עצמו עבר E2E; RMVPE עדיין לא
המרת קול    ✅       🟡
הזזת גובה   ✅       —

✅ מסלול ייצור מאומת · 🟡 תאימות/מימוש מסוים בלבד · ❌ נכשל
```

העומסים חיים ב-`svc_engine/compute/verify.py` ומשמשים גם את ה-Spike וגם את הפקודה
למשתמש. אין שתי גרסאות של אותה בדיקה.
