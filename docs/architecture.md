# ארכיטקטורה ותכנון UX

**עודכן:** 19 באוגוסט 2026 — Phase 11.

---

## 1. עקרונות היסוד

1. **הפרדה מוחלטת בין מנוע לממשק.** המנוע לא יודע שקיים ממשק. הממשק לא מייבא PyTorch.
2. **המנוע רץ בתהליך (process) נפרד.** קריסה, נעילה או OOM במנוע לא הורגים את החלון.
   ביטול משימה = הרג התהליך. פשוט ובטוח.
3. **כל שלב במנוע הוא צעד עצמאי עם cache.** אם שלב 6 נכשל, שלבים 1–5 לא רצים שוב.
4. **שום מונח טכני לא דולף למשתמש.** כל הודעה בממשק עוברת שכבת "תרגום לעברית פשוטה".
5. **הכול מקומי.** אין שליחת שמע לשום שרת. יציאה לרשת רק להורדת מודלים.
6. 🆕 **שום מודל AI חיצוני לא נצרך ישירות.** כל מנוע — הפרדה, המרה, זיהוי F0, הזזת גובה —
   יושב מאחורי מתאם (adapter) מוגדר. החלפת מנוע היא החלפת מחלקה אחת, לא שכתוב.
7. 🆕 **הליבה נבנית כאילו התוכנה תופץ.** אין תלויות GPL בקוד שנארז. רכיבי GPL
   מותרים רק בכלי פיתוח ובנצ'מרק, ובסביבה מבודדת.

## 3א. 🆕 המתאמים (Adapters) — הלב של אי-הנעילה

ארבעה ממשקים מוגדרים. כל אחד מהם מיושם ע"י מנוע אחד או יותר, וניתן להחלפה מלאה.

### `ConversionBackend`

```python
class ConversionBackend(Protocol):
    name: str
    def load(self, voice: VoiceModel) -> None: ...
    def convert(self, audio: AudioBuffer, f0: F0Curve,
                semitones: int, params: ConversionParams) -> AudioBuffer: ...
    def unload(self) -> None: ...
    def capabilities(self) -> BackendCapabilities: ...   # תומך F0 חיצוני? formant shift? zero-shot?
```

**מימושים מתוכננים:**

| מימוש | מתי | סטטוס |
|--------|-----|--------|
| `RVCv2Backend` | MVP | ✅ ברירת מחדל |
| `DDSPSVCBackend` | Phase 10 | 🔬 benchmark |
| `SeedVCBackend` | Phase 10 | 🔬 **בסביבה מבודדת בלבד** (GPL + בארכיון) |
| מנוע עתידי כלשהו | לכשיופיע | — |

> **הבהרה:** המתאם הזה **אינו** קיים כי מחכים ל-RVCv3. בדקתי — **RVCv3 לא שוחרר**;
> הטאג האחרון של RVC-Project הוא `2.3.260718` (v2), ו-v3 מובטח ב-README מאז 2023.
> המתאם קיים כי **התחום זז מהר ואסור שהחלפת מנוע תדרוש שכתוב.**

### `SeparationBackend`
מימושים: `AudioSeparatorBackend` (ברירת מחדל), `PymssBackend`.

### `PitchShifter`
מימושים: `PythonStretchShifter` (MIT — **ברירת מחדל**), `RubberBandShifter` (GPL — פיתוח בלבד, לא נארז).

### `F0Extractor`
מימושים: `RmvpeExtractor` (ברירת מחדל), `FcpeExtractor` (Preview), `SwiftF0Extractor` (מועמד).

## 3ג. 🆕 שכבת החומרה — שלושה מסלולי ביצוע

SongVoice תומכת בשלושה מסלולים **כיעדי ליבה**, לא כגיבויים זה לזה:

| מסלול | חומרה | הערה |
|--------|--------|------|
| `cuda` | כרטיסי NVIDIA | יעד תאימות נדרש |
| `xpu` | Intel Arc, ו-Core Ultra עם Arc משולב | **יעד ליבה**, דרך PyTorch XPU הרשמי |
| `cpu` | כל מחשב | גיבוי אוניברסלי |

**סדר העדפה:** `cuda` ← `xpu` ← `cpu`.

### הרכיבים

```python
class ComputeBackend(StrEnum):
    CUDA = "cuda"
    XPU  = "xpu"
    CPU  = "cpu"

class DeviceManager:
    def detect(self)             -> list[DeviceInfo]   # מה קיים בפועל
    def available_backends(self) -> list[ComputeBackend]
    def preferred(self)          -> DeviceInfo          # הכי מהיר שקיים
    def select(self, allowed)    -> DeviceInfo          # הכי מהיר מתוך מה שמותר
```

### ⭐ כלל ההוכחה

> **רכיב נחשב נתמך על מאיץ רק אחרי שעומס אמיתי רץ עליו והחזיר תוצאה נכונה.**
> התקנה נקייה, ייבוא מוצלח, או `is_available() == True` — **לא מוכיחים כלום.**
> מה שלא הוכח, רץ על CPU.

הסיבה: "נתמך" שגוי לא מתגלה עכשיו — הוא מתגלה כתקלה מסתורית באמצע עיבוד שיר.

זה מיוצג ב-`SupportMatrix`, עם שלוש רמות הוכחה:

| רמה | מה זה אומר | מספיק לייצור? |
|------|-------------|----------------|
| `none` | מעולם לא רץ על המאיץ הזה | ❌ |
| `ops` | סט האופרטורים שהרכיב צריך רץ בהצלחה | ✅ |
| `end_to_end` | המודל האמיתי רץ מקצה לקצה | ✅ |

המטריצה נכתבת אוטומטית ע"י ה-Compatibility Spike אל
`src/svc_engine/data/compute-support.json`, על סמך מה שבאמת רץ על המכונה.

### בחירה לכל שלב בנפרד

```python
device = matrix.device_for(Component.SEPARATION, manager)
hint   = DeviceHint.from_device(device)
```

**אין הנחה שמסלול אחד חייב לעבוד לכל הרכיבים.** אם ההפרדה לא רצה על Intel אבל
זיהוי הגובה כן — ההפרדה תרוץ על CPU והשאר על Intel, באותה עבודה.
`JobRunner` בוחר את המסלול המהיר שאומת, שלב אחר שלב.

`pitch_shift` הוא מקרה מיוחד: `python-stretch` היא ספריית DSP ב-C++ בלי מסלול GPU
כלל. CPU שם הוא המקום הנכון לעבודה, לא נסיגה מכישלון.

## 3ב. 🆕 סביבות ריצה — ותוכנית ב'

הסיכון: Roformer, RMVPE, RVC ו-`python-stretch` נכתבו ע"י אנשים שונים בשנים שונות.
אין ערובה שקיימת מטריצת תלויות אחת שמריצה את כולם.

| תרחיש | ארכיטקטורה | מתי |
|--------|-------------|-----|
| **תוכנית א' (מועדפת)** | סביבת Python אחת. מנוע אחד, תהליך אחד. | אם ה-Spike של Phase 1 מצליח |
| **תוכנית ב' (גיבוי מוגדר מראש)** | **שתי סביבות Python נפרדות** — `env-sep` להפרדה, `env-vc` להמרה — שמתקשרות דרך קבצי WAV בתיקיית עבודה משותפת ו-JSON למטא-דאטה | אם אין מטריצה משותפת |

**למה זה בטוח:** ה-`JobRunner` כבר מעביר קבצים בין צעדים. במעבר לתוכנית ב' משתנה רק
**איפה** רץ כל צעד, לא **מה** הוא עושה. שאר התוכנה לא יודעת מזה.

**סביבה שלישית — `env-bench`:** מבודדת לחלוטין, לא נארזת, מכילה את המנועים
לבנצ'מרק בלבד (Seed-VC ודומיו). **אין לה שום נגיעה במטריצה הנעולה של הליבה.**

Phase 10 מממשת את הגבול כתיקיית coordinator אחת שבתוכה runtime נפרד לכל מנוע:
`env-bench/runtimes/seed/.venv` ו־`env-bench/runtimes/ddsp/.venv`. ההפרדה הפנימית
נדרשת כי מטריצות Torch/NumPy של המנועים סותרות זו את זו. הליבה מפעילה רק פקודת
subprocess שמחזירה WAV; אין import, dependency או checkpoint משותף. Hatch אורז
במפורש רק `src/svc_engine` ו־`src/svc_app`, וכל `runtimes/` מוחרג מ־Git.
כל variant מוכנס ב־Windows ל־Job Object עם `KILL_ON_JOB_CLOSE`: timeout מסיים
וממתין לכל העץ, ו־RAM/VRAM מסוכמים מכל ה־PIDs ב־Job. ב־POSIX משמשת session/process
group נפרדת עם גילוי descendants כ־fallback.

## 4. מודל המשימה (Job)

משימה = גרף של צעדים. כל צעד:

```
Step:
  id            "separate_main"
  inputs        [hash של קבצי הקלט + כל הפרמטרים]
  cache_key     sha256(inputs)          ← אם קיים ב-cache, מדלגים
  outputs       [נתיבי קבצים]
  vram_hint     כמה זיכרון GPU צפוי
  cancellable   True
  progress      0.0 – 1.0
```

**התאוששות מתקלה:** מצב המשימה נשמר ל-JSON אחרי כל צעד. אם התוכנה נסגרה באמצע —
בפתיחה הבאה מוצג "מצאנו עבודה שלא הסתיימה. להמשיך?" והיא ממשיכה מהצעד הבא.

**ביטול:** דגל ביטול נבדק בין צעדים ובתוך לולאות ארוכות. אם לא נענה תוך 3 שניות —
התהליך נהרג בכוח והקבצים הזמניים מנוקים.

### מימוש Phase 7

- `JobRunner` ממיין את הגרף טופולוגית, דוחה תלות חסרה/מחזור, ומשקלל התקדמות
  כוללת מהתקדמות כל צעד. פעולת צעד מקבלת רק `StepContext`, נתיבי תלויות ו־scratch
  ASCII; היא אינה יודעת על הממשק.
- מפתח cache הוא SHA-256 של מזהה+גרסת הצעד, פרמטרים קנוניים, **תוכן** קובצי הקלט
  ומפתחות התלויות. שינוי פרמטר בצעד מאוחר אינו מבטל cache של קודמיו.
- תוצרי צעד נכתבים תחילה ל־scratch, מועתקים לתיקייה זמנית, נבדקים בגודל וב־SHA-256,
  ורק אז מתפרסמים אטומית. manifest חלקי או פגום לעולם אינו cache hit.
- `jobs/<job_id>.json` נכתב ב־temp+`os.replace` לפני ואחרי כל מעבר מצב. אחרי kill,
  תוצרי קודמים מגיעים מה־cache והצעד שהיה `running` רץ מחדש.
- `CancellationToken` הוא המסלול הנקי. בגבול app/engine נסגרת בקשת ה־stdio;
  worker שלא משתף פעולה מקבל terminate/kill בתוך deadline כולל של שלוש שניות.
- `work/jobs/` מכיל רק scratch. הצלחה, כשל וביטול מנקים אותו; אחרי hard-kill הוא
  נשאר מקושר ל־snapshot ולכן אינו יתום, ונמחק בתחילת ההמשך. ניקוי תחזוקה מסיר רק
  תיקיות שאינן שייכות לעבודה recoverable.
- `cache/steps/` נאכף ב־LRU לפי `Settings.keep_cache_gb`; מפתחות של הריצה הנוכחית
  מוגנים מפינוי. תקלה בניקוי cache ישן אינה הופכת עבודה שכבר הושלמה לכישלון.
- `projects/` משתמש ב־JSON גרסאי אטומי ובעותק last-known-good; `db.sqlite` שומר
  היסטוריית מצב/התקדמות ב־WAL. RPC חושף list/load/save, recovery, history ו־cleanup
  כנתונים בלבד — לעולם לא callable שמגיע מהממשק.

### מימוש Phase 8

- `EngineClient` משגר את `svc serve` כתהליך נפרד. כל בקשה מסתיימת ב־Response יחיד;
  פעולות ארוכות יכולות לשלוח לפניו אירועי `progress` מזוהים לפי request id. ה־GUI
  קורא רק JSON ואינו מייבא `torch`, ‏`numpy` או ספריית AI אחרת.
- `workflows/cover.py` בונה לכל Preview וקאבר גרף `JobRunner` אמיתי: `separate` →
  `analyze` → `render` → `deliver`. כל צעד מפרסם קבצים ל־`StepCache`; בקשת השחזור
  נשמרת אטומית תחת `jobs/requests/`, ולכן hard-kill ממשיך מהצעד האחרון שהושלם.
  Preview נכתב ל־`work/previews`; קאבר מלא נכתב ליד השיר בשם שאינו דורס קובץ קיים.
- `jobs.recoverable` מצרף לעבודת קאבר את המקור, הקול וסוג העבודה. פתיחת ה־GUI
  מציעה להמשיך את העבודה; `covers.resume` משחזר את אותו גרף ואותם פרמטרים.
- האשף הוא מכונת מצבים מפורשת: שיר → קול → איכות → עיבוד → המלצה → Preview →
  תוצאה. ניווט למסכים אחרים נעול בזמן עיבוד; ביטול סוגר את תהליך המנוע והקריאה
  החסומה משתחררת, בלי להקפיא את event loop של Qt.
- כל הטקסט בממשק עברי ומוגדר RTL ברמת `QApplication` ו־`MainWindow`. נתיבי קבצים,
  שמות פורמטים ומספרים נשארים ביחידות תצוגה מבודדות. `tools/bench_gui.py` מצלם את
  שבעת מצבי האשף ואת קולות/פרויקטים/הגדרות ומאמת ירושת RTL בכל עץ הווידג'טים.
- `i18n/he.py` ממפה כל `ErrorCode` לכותרת אנושית ולפעולה מוצעת. פרטי חריגה ו־stack
  trace נשארים במנוע ובלוג; הם אינם מוצגים בחלון.

**טיפול ב-OOM:** מנהל VRAM מרכזי. כשנתפסת שגיאת OOM:
`chunk ÷ 2` → נסה שוב → `batch = 1` → נסה שוב → `overlap` מינימלי → נסה שוב → CPU.
בכל שלב הודעה למשתמש: *"מתאימים את ההגדרות לכרטיס המסך… (ניסיון 2 מתוך 4)"*.

### 🆕 `quality_vs_shift` — למה זה קיים

בגרסה הקודמת פונקציית העלות של מנוע המנעד הכילה "קנס פורמנטים" (`w₅`) שהיה **מספר שהומצא**.
זה היה תיקון מוצדק בביקורת: הזזת אוקטבה אינה "חינם" מבחינת איכות הקול, גם אם היא
חינם מבחינת הסולם של הפלייבק.

**הפתרון:** בעת ייבוא או סיום אימון של קול, המנוע מריץ **מדידה חד-פעמית** —
המרת דגימת בדיקה קצרה בכמה הזזות, ומדידת דמיון דובר וספירת artifacts בכל אחת.
העקומה נשמרת בפרופיל.

**מכאן:** `cost(s)` משתמש בערך **שנמדד על הקול הזה עם המנוע הזה**, לא בהנחה.
המדידה חוזרת אוטומטית אם מחליפים `ConversionBackend`.

**עלות:** בערך 1–2 דקות פעם אחת לכל קול. רץ ברקע בסיום האימון או הייבוא.

**בממשק המשתמש רואה:** שם, תמונה, "מתאים לשירה גברית בטווח בינוני", כפתור השמעה,
נורית תקינות ירוקה/אדומה. **לא רואה:** `.pth`, `.index`, נתיבים, sample rate.

## 6. מנהל המודלים וההורדות

**רישום מודלים (`models.json`)** — נשמר בריפו, מתעדכן עם האפליקציה:
```json

  "id": "sep_bs_roformer_leap",
  "kind": "separation",

  "size_mb": 630,
  "sha256": "…",
  "urls": ["<המראה שלנו>", "<המקור המקורי>"],
  "requires": []
}
```

**Download Manager:**
- הורדה מקבילה עם HTTP Range → **Pause/Resume אמיתי**
- אימות SHA-256 בסיום; קובץ פגום נמחק ומורד שוב
- Retry עם השהיה גוברת (3 ניסיונות), ואז מעבר למראה חלופית
- הודעת שגיאה בעברית פשוטה: *"ההורדה נכשלה. בדוק את חיבור האינטרנט ונסה שוב."* + כפתור "נסה שוב"

**חובה (סיכון #1 במחקר):** נשקף את כל המודלים לריפו HuggingFace פרטי משלנו.
מודלים בקהילה נעלמים — ראינו שרק ~40% מהקטלוג של audio-separator עדיין חי.

## 7. תכנון ה-UX

### 7.1 המסע במצב פשוט

```
①  שיר      →  ②  קול      →  ③  ניתוח     →  ④  האזנה   →  ⑤  תוצאה
   גרירה         כרטיסיות       אוטומטי         Preview      נגן + ייצוא
   לתוך          קולות +        + המלצה         + אישור
   החלון         חיפוש          בעברית
```

**מסך 1 — השיר**
אזור גרירה גדול במרכז: *"גרור לכאן שיר"*. מתחת: כפתור "בחר קובץ" ורשימת שירים אחרונים.
אחרי טעינה: שם השיר, אורך, וצורת גל.

**מסך 2 — הקול**
רשת של כרטיסי קול: תמונה, שם, תיאור בעברית ("קול גברי, טווח בינוני"), כפתור ▶ להשמעה.
כרטיס אחרון: **+ הוסף קול חדש**.

**מסך 3 — רמת איכות (בחירה אחת)**
שלושה כפתורים גדולים: **מהיר** / **מאוזן (מומלץ)** / **איכות מרבית**.
לכל אחד: הערכת זמן. זהו — לוחצים **התחל**.

**מסך 4 — עיבוד**
פס התקדמות אחד גדול + משפט אחד שמשתנה:
- *"מפרידים את השירה מהמוזיקה…"*
- *"מנתחים את גובה הקול…"*
- *"ממירים את הקול…"*
- *"מחברים הכול יחד…"*

**אף פעם לא:** לוגים, אחוזי VRAM, שמות מודלים, פקודות.
בפינה: קישור זעיר "פרטים טכניים" שפותח את הלוג — למי שרוצה.

**מסך 5 — ההמלצה (מופיע אחרי הניתוח)**
כרטיס בהיר עם ההסבר, לדוגמה:

> 🎵 **בדקנו את השיר ואת הקול שבחרת**
> השיר גבוה יחסית לקול "יוסי".
>
> **✅ מומלץ:** להוריד את השירה באוקטבה שלמה.
> המוזיקה נשארת בדיוק כמו שהיא.
>
> [ אישור ]   [ אפשרויות אחרות ▾ ]

**מסך 6 — Preview**
נגן עם שני כפתורים: **מקור** / **התוצאה**, מעבר חלק ביניהם באותה נקודת זמן.
מתחת: *"נשמע טוב? [ המשך לשיר המלא ]  [ שנה משהו ]"*

**מסך 7 — התוצאה**
נגן מלא, כפתור **שמור**, כפתור **פתח תיקייה**, כפתור **התחל שיר חדש**.

### 7.2 מצב מתקדם

מתג "מתקדם" בפינה. פותח פאנל צדדי (לא מסך חדש — כדי לא לשבור את הזרימה) עם קבוצות מקופלות:

| קבוצה | מה בפנים |
|-------|----------|
| הפרדה | מודל, Ensemble, DeReverb, ווקאלים מלווים, overlap |
| גובה | חצאי טונים ידני, הזזת פלייבק, formant, ריכוך קפיצות |
| המרת קול | מודל, index_rate, protect, rms_mix, שיטת F0 |
| מיקס | ווליום ווקאל/פלייבק, LUFS יעד, לימיטר, כמות הדהוד |
| מערכת | GPU, גודל chunk, מספר תהליכים, תיקיית פלט |

**כל שדה מלווה ב-ⓘ שמסביר במשפט אחד בעברית.**
כפתור "החזר לברירות מחדל" תמיד זמין.

### 7.3 עיצוב

- **RTL מלא** דרך `QGuiApplication.setLayoutDirection(Qt.RightToLeft)`.
- פונט: **Rubik** או **Assistant** (Google Fonts, רישיון OFL, נארוז אותם).
- מצב כהה כברירת מחדל + מצב בהיר.
- טקסט מעורב עברית/מספרים/אנגלית — עטיפה בתווי bidi מפורשים כדי למנוע קפיצות.
- אנימציות עדינות בלבד (150–250ms), בלי "ריקודים".

## 9. תוכנית Git

**ריפו:** פרטי, ב-GitHub.

**ענפים:**
- `main` — תמיד עובד. כל שלב שהושלם מתמזג לכאן.
- `phase/N-שם` — ענף עבודה לכל שלב. נמחק אחרי מיזוג.

**קומיטים:** [Conventional Commits](https://www.conventionalcommits.org) —
`feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `build:`.

**גרסאות:** SemVer. תגית בסוף כל שלב: `v0.1.0` (Phase 1), `v0.2.0` (Phase 2)…
`v1.0.0` = השחרור הראשון המלא.

**CI (GitHub Actions), על Windows runner:**
1. `ruff` (בדיקת סגנון) + `mypy` (בדיקת טיפוסים)
2. `pytest tests/unit` — מהיר, בלי GPU
3. בדיקת הגבול: `svc_app` לא מייבא torch, `svc_engine` לא מייבא PySide6
4. בניית ה-installer — רק על תגיות

**מה נשאר ידני אצלך:** רק לאשר merge ולהריץ פקודה כשאני נותן לך אותה במפורש.

## 11. אריזה ועדכונים

PyInstaller בונה `onedir` עם Python 3.11, Torch/Intel XPU, Qt ו־ffmpeg LGPL
מוטבעים. `SongVoiceLauncher.exe` הוא נקודת הכניסה היציבה; הוא מחיל update ממתין
לפני פתיחת `SongVoice.exe`. אותו executable מפעיל במצבים פנימיים את שרת המנוע
ואת worker האימון, ולכן אף subprocess אינו תלוי ב־`python.exe` חיצוני או מציג console.

הפעלה ראשונה כותבת `setup-complete.json` רק אחרי זיהוי backend, אימות runtime,
התקנת מודלי הליבה לפי size+SHA והרצת health. ה־offline installer מזין מראש את
אותו model store. updater מוריד manifest ו־ZIP ב־HTTPS, מאמת size+SHA, מחלץ לתיקיית
staging בטוחה, מגבה קבצים מוחלפים ושומר transaction receipt; כל כשל מחזיר את
ההתקנה למצב הקודם. `env-bench` וכל מנוע benchmark מוחרגים מה־spec ומה־installer.
